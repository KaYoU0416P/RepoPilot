# 素材：RepoPilot（以下全部为实测事实）

**一句话**：把 Coding Agent 接进真实研发流程的后端服务。
不是「能改代码的脚本」，是 `GitHub Issue → 入队 → Agent 修复 → 人工审批 → 开 PR`
这条业务链路。

**仓库**：https://gitee.com/KaYoU0416P/RepoPilot
**技术栈**：Python · FastAPI · LangGraph · Pydantic v2 · asyncio ·
PostgreSQL 17 · asyncpg · Docker · OpenTelemetry · MCP
**规模**：403 个自动化测试全绿、34 次提交、约 7000 行源码 + 4800 行测试。
所有设计取舍和已知缺口写在 `docs/` 里，实测存档在 `docs/evidence/`。

## 一、可量化的 Agent 质量（A 版重点）

- 自建 **18 个 case 的评测基准集**：15 个真实 bug 形态（差一错误、跨文件常量、
  时区、浮点金额、需要改测试、无解题…）+ 3 个提示注入。
- 每个 case **跑 3 轮**，区分三个指标：平均成功率 93% / **可靠成功率 89%**
  （每一轮都对才算）/ 乐观成功率 94%。**报「可靠」那个**，
  因为接进 CI 关心的不是"平均能修对"而是"会不会稳定修对"。
- 成本：**平均修对一个 bug $0.0080**（失败烧的钱也摊进去），
  3.3 次 LLM 调用 / case。
- **评测集自带自检**：第一次跑出 72%，查下去发现 **9 次失败里有 6 次是我自己的
  测试用例写错了**（可见测试和正确答案互斥）。修完才有 89%。
  —— 结论是「评测集自己也需要被评测」。
- 最硬的一条负面结论：一道无解题上，模型 3 轮里有 2 轮**宣称解决了**。
  「这个 Agent 不知道自己不知道」，这正是人工审批闸门存在的理由。

## 二、提示注入防护 + A/B 对照实验（A 版重点，最难被复制的一条）

- 防的是「Issue 正文里藏指令」。做法：**中和 + 截断 + 分隔符包围 +
  在 system 里声明「分隔符里是数据不是指令」**。思路等同参数化查询 ——
  必须先中和用户内容里的闭合标签，否则围栏只是装饰。
- **关键是做了 A/B 对照**：评测里注入样本 9/9 全抵抗住，但那个数字
  **证明不了防护有效** —— 它和「模型本来就不上当」无法区分。
  所以关掉防御再跑一遍：**攻击载荷落地从 0/9 变成 4/9**。
- 刻意**不在生产代码里留「关闭防御」的开关**（一个能被环境变量关掉的安全控制
  本身就是漏洞），实验用 monkeypatch 做。
- 诚实边界：这是概率性防御；且只管 `task` 那条路，
  载荷藏在**工具读回来的文件内容**里目前挡不住。

## 三、三层隔离跑不可信代码（A/B 版都可用）

- 路径收敛（拒绝绝对路径 / `..` / 符号链接逃逸）→ 拒绝 `.git/` 控制面 →
  一次性容器（`--network none`、`--cap-drop ALL`、内存/PID 上限、只读根、非 root）。
- **同一份攻击探针实测**：本地子进程**越狱 4 项**
  （能联网、能看见 `/Users`、`~/.ssh`、`.env` 里的 API key），容器 **0 项**。
  —— 也就是模型写的测试代码既能读到密钥，又有网络把它发出去。
- 过程中**查出两个真实提权路径**：
  1. 往 `.git/config` 写 `core.fsmonitor = /bin/sh -c '...'`，
     而 `git diff` 是在宿主机上跑的 → 完整的宿主机代码执行。
  2. `shutil.copytree` 默认跟着符号链接**把内容拷过来** → 陌生仓库里一个指向
     `~/.ssh/id_rsa` 的链接，私钥会变成 workspace 里的真文件、进 diff、进 PR。
- 刻意**没有通用 shell 工具**，唯一的执行类工具是 `run_tests`，命令行写死。

## 四、后端可靠性（B 版重点）

- **`runs` 表兼任任务队列**：`SELECT ... FOR UPDATE SKIP LOCKED` + 租约 +
  心跳续租。worker 崩了租约到期任务自动被别人接手（对应 MQ 的 ack 超时重投）。
  队列和业务表同一张表 → 入队和业务写入天然同事务，不存在双写不一致。
- **8 状态表驱动状态机**，流转表是唯一真相来源，终态从表推导。
  **结构上不存在 `running → published` 这条边** —— 审批闸门不是靠 if 判断，
  是靠状态机里没有那条边。测试用 BFS 验证每个活跃状态都能走到终态。
- **两层幂等**：webhook 用 `X-GitHub-Delivery` 当幂等键（唯一约束 +
  `ON CONFLICT DO NOTHING`）；开 PR 发生在别人家系统里、数据库约束管不着，
  所以自己造键 —— 分支名 `repopilot/run-<id前8位>` 从 run_id 算出来，
  **不带随机数不带时间戳**，崩在任何一步重试都不会开出第二个 PR。
- 踩过的坑：commit 的 `GIT_AUTHOR_DATE` 默认取当下，时间戳会进 commit SHA，
  重试算出另一个 SHA，push 变 non-fast-forward —— 幂等直接失效。
  **表现为「测试偶尔失败」**，钉死日期才真正确定。
- 失败分类：`PublishError`（4xx / diff 打不上）不重试；5xx / 网络抖动
  靠租约过期自动重试。判据是「错在谁」。
- 优雅停机、两层并发限流（worker 并发 × 单 run 内工具并发）、
  SSE 实时推送每个节点的进度。

## 五、成本控制与可观测（A 版重点，B 版可压缩）

- 每次 LLM 调用累加 usage，按模型单价表算钱。
  **查不到单价的模型成本报 `None` 不报 0** ——
  把"不知道"报成"免费"是成本报表最容易骗自己的地方。
- **per-run 的 token / 美元双预算熔断**：`max_retries` 是次数预算，
  拦不住"在次数以内烧掉任意多 token"（真实评测里撞到过 3 次：无解题上模型
  反复推理，一次调用烧光 16K 输出 token，产出为零）。
  **阈值取自 54 次真实 run 的分布**（中位 4.2K、p90 9K、最大 39K，上限设 120K），
  不是拍脑袋。
- OpenTelemetry **三层 span**（run / node / tool），靠 `ContextVar` 自动串父子关系。
- 结构化日志全局携带 `run_id`；高危工具调用单独走审计日志。

## 六、API 鉴权与审计（A/B 版都可用，B 版尤其对口）

- Bearer token + 权限位。**刻意不做 OAuth/JWT**：调用方是 CI 机器人和几个人，
  不是"任意第三方应用代表用户访问"。**认证方案要配得上威胁模型。**
- **默认拒绝**：鉴权挂在 `APIRouter(dependencies=...)` 上而不是逐个路由加 ——
  逐个加的失败形态是「新接口忘了加就是公开的」，**而且不会报错**。
  公开接口只有 `/health` 和 `/webhooks/github`，在另一个 router 里。
  （思路照搬 Spring Security 的 `anyRequest().authenticated()` + 显式白名单。）
- **审批要单独的权限位**：开 run 的那把 key 批不了自己开的 run，
  否则审批闸门是装饰品。CI 机器人拿 `run`，人拿 `run,approve`。
- **`decided_by` 取自认证身份而不是请求体**：以前它是请求体里的字段，
  意味着审批流水上"谁批的"是**被审计的人自己填的**，随手写 "CTO" 就行。
  —— **审计字段不能由被审计者提供。**
- webhook 验签用 `hmac.compare_digest` 常数时间比较；密钥未配置时
  **fail closed**（拒绝所有）而不是"跳过验签"。
